## Teaching loop — read this first

This is a **capstone learning project**, not a delivery-first project. The rules below are non-negotiable:

1. **Explain before you implement — always.** For each step: explain (a) what we're building, (b) the real-world EDA/hardware concept, (c) your plan. Then **wait for the user to say "go"** before writing code.
2. **Explain TCL and Make concepts the first time they appear.** Inline comments required; no unexplained "magic."
3. **Work one phase per session.** Build it, make it runnable, update all docs, then stop.
4. **At the start of every session:** read `docs/HANDOFF.md`, verify the flow still runs, state the plan, wait for go-ahead.
5. **At the end of every session:** update `docs/HANDOFF.md`, write `docs/sessions/session-NN.md`, add/extend `docs/notes/`.

## Commands

```bash
make help       # show all targets (default target)
make rtl        # generate SystemVerilog from spec/irq_ctrl.yaml → gen/rtl/irq_ctrl.sv
make header     # generate C firmware header → gen/include/ (Phase 2, currently stubbed)
make docs       # generate register-map docs → gen/docs/ (Phase 3, currently stubbed)
make validate   # lint the register spec (Phase 1, currently stubbed)
make check      # consistency gate — diff gen/ vs spec (Phase 4, currently stubbed)
make all        # rtl + header + docs + validate + check
make clean      # remove gen/rtl/, gen/include/, gen/docs/, gen/*_manifest.json
```

Run the engine directly (bypasses Make/TCL, useful for debugging):
```bash
python3 tools/reggen/reggen_engine.py --spec spec/irq_ctrl.yaml --outdir gen --output rtl
```

Dependencies: `python3`, `tclsh`, `make`, `pyyaml` (`pip install pyyaml`).

## Architecture

The flow has three layers stacked on a single source of truth:

```
spec/irq_ctrl.yaml          ← single source of truth (YAML register spec)
        │
        ▼
Makefile                    ← front door; calls tclsh with flow/run/gen.tcl
        │
        ▼
flow/run/gen.tcl            ← designer run script; sources the tool API, then calls commands
        │  sources
        ▼
tools/reggen/reggen.tcl     ← TCL tool API (read_spec, set_output_dir, generate_*)
        │  exec python3
        ▼
tools/reggen/reggen_engine.py  ← Python engine: YAML parsing + APB RTL generation
        │
        ▼
gen/rtl/irq_ctrl.sv         ← GENERATED: APB register block (SystemVerilog)
gen/irq_ctrl_manifest.json  ← GENERATED: run manifest (JSON)
```

**The TCL/Python split is intentional:** TCL is the API skin (mirrors real EDA tool interfaces like Synopsys DC or Cadence Genus); Python does the real work. This pattern is a core part of what the project demonstrates.

**APB RTL structure** (generated by `generate_rtl` in `reggen_engine.py`):
- One storage flip-flop per `rw` field; `ro` fields are hardware input ports
- Sequential write logic: on `PSEL & PENABLE & PWRITE`, decode `PADDR[7:0]`, write `PWDATA` into matching flops
- Combinational read mux: drive `PRDATA` from field values based on `PADDR[7:0]`
- `PREADY` tied high (zero wait-state)

## Register spec format

```yaml
block: irq_ctrl           # → module name
base_addr: 0x40001000
reg_width: 32
registers:
  - name: CTRL
    offset: 0x00
    fields:
      - { name: ENABLE, bits: "0",   access: rw, reset: 0, desc: "..." }
      - { name: MODE,   bits: "2:1", access: rw, reset: 0, desc: "..." }
  - name: STATUS
    offset: 0x04
    fields:
      - { name: BUSY, bits: "0", access: ro, reset: 0, desc: "..." }
```

Access types: `rw` (SW read/write), `ro` (HW-driven, SW read-only), `wo`, `w1c`, `rclr` — see `docs/notes/` for hardware semantics.

## Documentation system

Every session must maintain:
- `docs/HANDOFF.md` — living state: what works, how to resume, what's next
- `docs/sessions/session-NN.md` — per-session log including interview-framed reflection
- `docs/notes/<concept>.md` — beginner-friendly notes (what, why, real-world counterpart)

Generated files in `gen/` are **checked in** — this is intentional so the Phase 4 consistency checker can detect drift between the spec and the committed outputs.
